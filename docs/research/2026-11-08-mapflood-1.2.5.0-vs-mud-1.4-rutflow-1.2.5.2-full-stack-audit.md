## 1. Distinct functional advances worth studying

### MF125-01 — higher resolution, broader/more intense flood simulation

- `MapFlood.GRID_MAX_CELLS` raised **512→1024 per axis**. Nominal min cell still 4 m: **2km map →512² 4m cells**; **4× map ~4km→1024² 4m cells** (previously 8m); **16× ~8km→1024² 8m cells** (previously 16m). On 4km maps this is up to **4× as many scalar cells**, before extra basin indices/polygons/mesh buffers; do not claim measured CPU impact.
- Flood severity now allows road/river rises **up to 0.5/1.5/3/6m** per four modes, and an additional optional maximum height setting of up to 15m. Previous v10 base levels capped ~0.5–1.45m. New default **strength=2 (MEDIUM)**, jobs enabled, pumping enabled, crop damage enabled. Use low/disabled features on a cloned save: unreviewed settings migration to this new severity profile should not be trusted in a productive save.
- Server map-wide catchments, road depressions, existing-water shoreline and water volume→height inversion remain, with better water-source/rivers and controlled drain rates. The basic saturation state is still **MapFlood's own independent field/global bucket**, not Mud 1.4 `FieldLocalWetness`/`LocalPuddleSystem`.
- Flood levels from MapFlood are horizontal and derived from stored volumes, unlike RutFlow's visually approximated micro-rut water sheets. But **even this higher 4m cell scale will not reliably represent an individual narrow RE rut**, particularly rut geometry modified after original map scan.

### MF125-02 — clean water / muddy flood transition and external water node visibility

`MapFloodCleanWater.lua` newly surveys external scene SHAPE nodes in a frame-bounded scan (and periodic follow-up), recognizes built-in clear-water regions via `underwaterFogColor`, and recognizes small other-mod puddle/rut water shapes by name. Associates them with MapFlood reservoir polygons/cells. At a flood level above the original water level, it switches the scene's owner-visible geometry with **entry 0.02m / exit 0.005m** hysteresis and original-state restoration; otherwise it progressively tints nearby clean rivers/lakes with muddy-flood shader colors.

This is real *visual continuity* work: clean river water need not instantly become uniformly dark over a whole map, and adjacent surface layers can avoid obvious z-fighting. There are per-frame mesh budgets, rescan on new placeables, and teleport/rejoin presentation refresh. **But**:
- It performs `setVisibility` and `setShaderParameter` on **other providers' SHAPE nodes**. Without a lease/owner API, later external mod updates can overwrite MapFlood, or MapFlood's unconditional restored original state can supersede a newer foreign change. No concrete live conflict proven.
- Generic name detector includes words like `water`, `rut` and `flow`, potentially matching other small visible shapes; fallback only attempts nodes with bounded radius and true flood coverage. This is not a vetted Mud integration contract.
- Mud's `LocalPuddleVisuals` water planes have **no WATER collision**, use their own reservoir authority and native `ShallowWaterSimulation` resource. Name/scene-node covering can perhaps hide some Mud visuals, but cannot merge volume, water level, wheel sink, ice collision or wetness. **Never treat water-node hiding as hydrological interoperability.**

### MF125-03 — persistent crop consequence within a session, with caveat

New `MapFloodCrops.lua` creates one approximately **8m×8m** surface sample per field polygon. Every ~2s real time it scans ≤**1,500 blocks/frame** and accumulates **game hours** of contiguous submergence where depth is **at least 0.05m**. Default `CROP_DEATH_H=12 game hours` times menu `cropTime=1`; **cropDamage ON by default**, even if jobs are subsequently disabled. The new simulation queues at most **12 native `FieldUpdateTask` operations per tick** to set the currently growing fruit type to its withered state and, if plowing-required option is enabled, clear the plow-level. For unowned eligible plots it may later create a native `PlowMission` if `jobs` is also ON. Uses native density-map tasks rather than writing raw custom crop textures.

**Exact source mock:** under a fictitious ~8m crop field, water depth 0.06m and 2,001ms of active simulation at time scale 21,600 (12.006 game hours), executing exact `MapFloodCrops.lua` sets first block `dead=true` and enqueues one crop-damage event; the flooded field's separate bucket `storage` reaches its own max 100. This validates branching, NOT actual GIANTS crop update, harvest compatibility or realistic agricultural threshold.

**Source lifecycle problem:** `f.crop.t`/`f.crop.dead` hold the contiguous 12-hour submergence history in Lua and **are not serialized** in `mapFlood.xml` or synced separately in code inspected. Save persists field `storage` and `ponded`, zone volume and mission data, **not individual crop submersion clocks**. A save/reload may reset pre-death submerged time even when the flood resumes. This is a source-proven persistence omission, not an observed in-game crop exploit. An upstream improvement would persist block/cell exposure by stable field/coordinates and schema revision or derive from a compatible existing source.

**Agronomic conflict scope:** Realistic Harvesting/SoilCompaction and native contracts already own crop maturity/growth, plowing/field state and economy. A new mod with its own sampled crop death and plow missions changes real agricultural save state. Users prioritizing RE terrain physics acceptance should initially **turn cropDamage and jobs OFF**; this is not a cosmetic safety toggle.

### MF125-04 — external intake is now really wired

The v10 audit documented `MapFlood:onExternalWaterIntake(vehicle, liters)` as **unreferenced** in shipped source. In v1.2.5 new `MapFloodTankWater.lua` installs a **global `FillUnit.addFillUnitFillLevel` wrapper** at **script-load time**, optionally multiplies accepted non-station WATER inflow under `pumpRate` and, after invoking the original, calls `MapFlood:onExternalWaterIntake(self, applied)` on authorized server-water calls. `onExternalWaterIntake` checks server/zone readiness, vehicle/fill trigger currently active, nearby flooded zone and known `vehicle.waterY` differences before deducting liters. The old source-level unconnected claim is thus **fixed at the call-site level**.

**Limits to verify:** The hook is **global and installed independent of menu pumping ON/OFF**, as is the existing global `FillUnit.onLoad` supported water type extension; it is not a per-vehicle API. The intake filter's post-call check does **not expressly exclude `ToolType.TRIGGER`** (although `spec.fillTrigger.isFilling` is checked by its callee); if a vehicle is simultaneously near a flood and filling through a scripted station or another mod with different trigger lifecycle, false attribution is possible. No real intake measurement or demonstrated false deduction. Hook wrappers must be inspected against MR/RMS/RE/RC and other fill mods before primary adoption.

### MF125-05 — pump PTO hooks moved earlier, not removed

The previous fixed-load concept persists: **+500 requested minimum motor RPM, +0.5 kNm PTO torque** when a recognized root is pumping, regardless of actual water head/flow/pump type/drive efficiency. `VehicleMotor.getRequiredMotorRpmRange` gets wrapped in `loadMap` even if the pumping setting is OFF; `PowerConsumer.getMaxPtoRpm` and `getTotalConsumedPtoTorque` are now wrapped at **script-load time** because the author notes that vehicle specialization methods may have copied pointers before `loadMap`. `Vehicle.getRequiresPower` is also wrapped to hold a pumping vehicle's engine on. This is technically thoughtful about GIANTS load order but **increases early owner/hook order sensitivity**, especially with RC/RE PTO, MR and RMS. It still isn't a versioned pump/workload provider.

**Design opportunity:** read-only pump telemetry **flow L/s, head/pressure m, shaft/drive origin and measured efficiency** → owner-supplied actual power/torque (P≈ρgQH/η), with a single motor/shaft provider. No global fake speed floor or constant torque. The old numeric PTO 0.5 kNm at 540 rpm implies ~28.3 kW before efficiencies (unit sanity only). RE does not need to absorb it merely because hydraulic pump gameplay exists.

### MF125-06 — larger contracts/UI and third-party physical scope

- Mission generators and contracts reworked: dynamic NPC employers (municipality/fire brigade/insurer etc), expiration, cooldowns, native `PlowMission` after flood crop death, faster mission cleanup and UI; useful *gameplay* concepts but may overlap user's existing contracts stack (BetterContracts, AdditionalContracts, AdvancedFarmManager, etc).
- `MapFloodCleanWater` includes visual pollution plume when a water tank discharges into clean lake/river; no source-proven true pollutant mass transport or water-quality ecosystem model.
- A higher-resolution grid and additional daily crop-state scans + node scans/material updates raise **performance question**, no FPS measurements. Pathological dirty-scene node scanning, million-cell raster setup and SWS shape pressure are more meaningful than counting Lua lines.
- Author advertises dedicated server support/late join and test-runner success for v1.2.5. **No live savegame load, mp, output-image test or vehicle gameplay proof from this audit.**

## 3. Three-way water-owner decision

| Mod/domain | MapFlood 1.2.5 | RutFlow 1.2.5.2 | Mud 1.4 |
| --- | --- | --- | --- |
| Authoritative rain/snow wetness, catchment and volume | **Own field bucket and map-wide floods** | No real mass solver, cosmetic fill | **Own local moisture and lowland puddle volumes** |
| Geographic scale | Flooded roads/rivers/fields; up to 1024² 4m samples on 4km | 6m tiles, ~0.25m local measured contour | ≤256² cells, ~16m samples on 4km |
| Physical effects | WATER collision, blocked traffic, pumping power hooks, crop changes | SWS visuals, player gfx | Mud sink/rolling/friction, surface water and real ice collision |
| Water visuals | Flood plane mesh; native water/material replacement/tint | Micro-rut overlay; checks MapFlood `getFloodAt` and yields when covered | Its own surface meshes; no generic WATER collision for visuals |
| Persistence | Server basin/field/contract data; crop exposure clocks not stored | Client-computed visual state | Server-owned puddle/ice and local soil moisture state |
| Cross-mod water integration | RutFlow visual masks; **none with Mud basin authority** | Recognizes MapFlood, not Mud | **Explicit source warning against MapFlood/RutFlow** |

**Primary stack decision:** Keep **Mud 1.4** as the authoritative local-water, tire/terrain-contact owner and, pending game acceptance, **RutFlow OFF**, **MapFlood OFF**. **Do not add MapFlood as an extra flood writer** on top of Mud. This is not claiming Mud supplies equivalent city-scale flood logistics; it demonstrably does not, and MapFlood is more than redundant in gameplay. But dual uncoordinated hydrology/soil buckets, overlapping SWS/visual ownership and the full-time pump/CVT hooks cost too much uncertainty in the existing RE terrain acceptance project.

**Experimental alternative** (cloned/disposable save): MapFlood 1.2.5 alone as the single flood hydrology owner (for flood jobs, pump logistics and crop dynamics) with Mud disabled, **low severity**, artificial rain OFF, floodGen=0, **cropDamage OFF**, **jobs OFF**, **pumping OFF**, optional puddles, monitor scan and flooding after rain. Test pumps/crops separately after validating hydrology, and compare a small truck/tractor in deep WATER collision. RutFlow can be added later in its matching author ecosystem as **optional visual-only overlay** with MapFlood coverage masks, but its client-only persistence and SWS budget still need actual game profiling. Note pumping OFF does not unhook global PTO or FillUnit wrappers.

A **further research-only isolation profile** of Mud puddles OFF with MapFlood ON is mechanically less overlapping on *water sheets*, but **still unsupported by the Mud developer**, still uses separate soil-moisture storage and global hooks, and must never be pitched as proven safe or as a simple RC patch target.

**Bridge verdict:** **No RC/RE runtime code changes** or version gate for MapFlood on source alone. Don't write a warning-suppression bridge or hide Mud visual water to conceal a real split water authority. A serious supported project would require a single *Hydrology/SurfaceWater owner* with typed moisture units/basin volume; map-wide event flooding as an optional high-level consumer of Mud catchment, carefully bounded per-region topographic change events and one water/mesh renderer; a separate bounded `PumpPowerDemand` provider and agronomic damage contract owned by crop/field specialists. Such collaboration needs explicit upstream APIs and permission, not changes to unlicensed third-party files or takeover of private tables.

### What RE can learn now (priority ordered)

1. **Non-destructive observations:** floods across roads, map catchments and native river overflow show how terrain and water dynamics can create logistics/road-work gameplay. **Not a prerequisite** to finish RE rut heightmap recovery.
2. **Geometry and material lifecycle:** source-aware bounded hiding/tinting of water, with correct foreign ownership and reversible state, is a positive UI pattern for future optional micro-rut overlay. No wholesale material/node traversal port.
3. **Agronomic consequences:** a duration-of-submergence input from canonical Mud water can feed native fruit/field damage and eventual plow contracts, but should be calibrated per crop, save exposure clocks and not duplicate RH/SoilCompaction/native crop stage. Not worth adding before soils stabilize.
4. **Real mechanical pump demand:** optional map flood gameplay could use **real workload power provenance**, linked to MR/RE PTO and RMS wear; separate AI/MP owner authorization from UI controls. No broad PowerConsumer patch without an actual reproducible pump.
5. **Incremental hydro update:** coarse catchment + local high-res rut microgrid geometry, only after committed geometry mutation notifications, is a research direction not an immediate obligation.
