# RutFlow 1.2.5.2 (successor of Water in Deep Tire Tracks) vs Mud 1.4.0.0 — source audit and active-stack choice

**Audit date:** 2026-11-07. **User question:** The earlier Water In Deep Tire Tracks is already enabled in their actual MR/Mud/Reifen/RMS/RC/RE game stack. Mud 1.4 has gained persistent puddle hydrology. Should the overlay remain, should both be bridged, or should only one own water? This audit answers **the installation/ownership decision**, not merely changelog discovery.

## Decision at a glance

**Main save with Mud 1.4 hydrology enabled: prefer Mud alone as the authoritative surface water/ice and mobility owner; do NOT run RutFlow 1.2.5.2 with its water surface simultaneously.**

This is **not** because RutFlow became useless: the latter has source-evident **6 m tiles, 0.5 m localized refined triangles, 0.25 m ground re-sampling and 100 m near-camera measured contour rendering** for small wheel ruts; Mud 1.4's volume/priority-flood topology is limited to **256×256** cells (~8 m on a 2km map or ~16 m on 4km). RutFlow can still depict narrow new RE geometric ruts better than Mud's coarse basin hydrology. But RutFlow supplies **an independent visual-level model**, no Mud-local wetness provider, no Mud-puddle suppression callback, and its public water API is **client-only**. Both register native SWS water planes in overlapping regions. Mud **explicitly detects RutFlow as incompatible** by source and repeats an incompatibility notice every four minutes when active, regardless of whether the user has disabled Mud puddles.

**Alternative controlled profile:** Mud 1.4 puddles OFF, RutFlow ON, RE ruts ON on a disposable save to evaluate narrow rut visual quality, while keeping Mud normal wetness/traction/sink for soil. This avoids two active *surface-water simulation* providers but can still show **decorative water whose presence/level disagrees with Mud's physical wetness**, and Mud's independent mod-presence warning may still appear. No assertion that this profile is approved for regular play without test.

Do not design a broad RC bridge merely to suppress a warning. A real coexistence patch would require explicit **source/ownership APIs**, not just a version allowlist.

## 1. What improved in the rewritten RutFlow (positive learning)

1. **Terrain-sensitive water line instead of only broad 6 m interpolated height:** `contourEnabled=true`, `contourRadius=100m`, `guardSpacing=0.25m`, per-tile sample and smoothing. The old `guardEnabled` is **false by default in 1.2.5.2**, because a new **measured contour surface** supersedes legacy edge-guard correction; release prose mentioning “Edge Guard” does not mean the old numerical guard is currently turned on. Re-evaluates near-camera geometry after planting/cultivation, helper marks and save/load with a background self-check age of 180 s and bounded `raysPerFrame=40`. It **reads native terrain height**, not a direct RE-generated ruts event, and does not change the heightmap.
2. **Localized displacement/refill:** under moving tires the surface can lower; bow wave is bounded and only triggered with existing water depth ≥**3 cm**, and refills with rain/soil moisture/snowmelt. Config uses `holdFreshMs=3000`, `refillSeconds=30` plus faster wet/rain options, 0.5 m fine triangles under active tracks, ≤120 active fine blocks and a ≤120 m wake influence around camera. This is **visual/particle water motion**, not authoritative mass/flow or wheel-resistance hydraulics.
3. **Native visual water interaction:** rice field material, mirrors, optional foam and wave velocity/depth via GIANTS `ShallowWaterSimulation`, and player-model/camera graphical offset down into ruts. The player graphics position changes are local presentation; not a new vehicle traction, body mass or terrain deformation solver. RutFlow makes client-side `addWaterPlane` / `addAreaGeometry` calls; another water owner can use the same engine service.
4. **Previous source bug corrected:** old WIT 0.9.1.5 cluster merge forgot the merged body's `sx/sz/n`; new `activateTile` merges these values. Loaded exact RutFlow Lua with minimal GIANTS mocks, activated (0,0), (2,0), joined via (1,0): final root reports **n=3 and sx=3** (correct), versus prior archival Lua mock showing **n=2**. Real gameplay manifestation not established.
5. **Save and namespace migration:** exports old `WaterInDeepTireTracks = RutFlow` alias; current `rutFlow.xml` loads legacy `waterInDeepTireTracks.xml` if needed, and local user `modSettings/RutFlow.xml` reads old `WaterInDeepTireTracks.xml`. A legacy mod in the folder is detected and its runtime `deleteMap` invoked, then update replaced with a no-op. **Remove old FS25_WaterInDeepTireTracks_MrHunter ZIP instead of trusting this runtime override in the primary stack**. Back up save and original XML before migrating. Client-local save append and lack of authority events still make dedicated MP persistence/join-in-progress **unverified**.
6. **Visible render budget is not zero:** `maxTiles=4000` and `viewDistance=750m` for retained geometry, `tilesPerFrame=2`, 40 ground rays/frame, active contours within 100m, `swsMaxShapes=1500` with 360m/480m registration hysteresis, 1s SWS refresh and all-vehicle scanning in client update. Former WIT limited visible SWS more tightly (256 shapes, 70m/100m). This is a richer but potentially more expensive client-local overlay; **no FPS measurement** has been conducted.

## 2. Source-backed incompatibility with Mud 1.4 water

### RF/MUD-01 HIGH — explicit Mud warning/detection

The exact user-provided Mud 1.4 ZIP `scripts/WaterModsConflictDialog.lua` targets **`MapFlood`, `RutFlow`, `RealTireWear`**. The RutFlow detector uses raw methods `buildTile`, `updateTiles`, `getWaterLevelAtWorldPos`, `readMoistureAt` and `CONFIG`, rather than just filename. Client message for RutFlow states that combined water/moisture/vehicle behavior is **incompatible and not recommended**; repeats at 240000 ms while present. A tiny `texlua` harness loading exact source for **both mods** with `g_modIsLoaded.FS25_RutFlow=true` reproduced `WaterModsConflictDialog:detect().RutFlow = {"FS25_RutFlow"}`.

**Meaning:** upstream Mud's developer has explicitly rejected combined support. This does **not by itself prove every combination crashes or changes wheel physics**, but it raises the adoption bar. Warning triggers on **mod presence**, not on whether its new surface-water toggle is enabled.

### RF/MUD-02 HIGH — RutFlow cannot reliably “yield” to Mud's water

RutFlow `updateCoverage` regards a tile as covered if:
- its recognized **MapFlood** object reports `getFloodAt` higher than the local water level, or
- a raycast using `CollisionFlag.WATER` finds a water surface above the RutFlow tile.

It **does not** query Mud's `LocalPuddleSystem`, `getDepthAt`, `getWheelMudStrength` or Mud local wetness. The exact Mud 1.4 `LocalPuddleSystem.lua` **explicitly comments that its own water *visual* planes have no WATER collision**, and `LocalPuddleVisuals.lua` creates surface meshes and registers them in ShallowWaterSimulation. So the RutFlow generic WATER-collision check **cannot be assumed to see Mud's rendered puddle sheets**. Mud's own overlap avoidance checks the native environment area's water surface, not RutFlow client-local sheets. Each can show water at independent levels in the same field depression, with duplicate water planes and SWS activity. **No actual in-game z-fighting/performance failure measured**; source establishes absence of reliable mutual suppression.

### RF/MUD-03 HIGH — independent water/soil moisture state; no direct Mud API

RutFlow `readMoistureAt(x,z)` tries **RWSM**, **Moisture System**, **MapFlood**, else **`weather:getGroundWetness()`**. It contains **zero `FieldLocalWetness` and `LocalPuddleSystem` references**. Mud 1.4 uses local hydrology, runoff, reservoir levels and per-cell wetness, with puddles allowed even in its simplified local-wetness-OFF mode. Consequently, **RutFlow's independent fillFraction is not the Mud basin's water mass** and not necessarily the same as Mud's local wheel sink/wetness.

Isolated Lua mock: available Mud `FieldLocalWetness:getEffectiveWetnessAt` returns **0.92** but none of RutFlow's explicitly supported sources available; game `getGroundWetness()=0.18`. Actual RutFlow `readMoistureAt(10,20)` returned **0.18** and selected source **"Spiel (groundWetness)"**, proving this fallback behavior. That is a valid source path, **not evidence that the game's current weather is actually 18%**. Moisture cache is 8m/cell for 8s, separate from Mud's dynamic state.

### RF/MUD-04 HIGH — client-only RutFlow water accessor is not a server hydrology provider

`getWaterLevelAtWorldPos` returns nil when `self.isClient` is false, or if a tile is not activated, is covered or has no visible fill. `getWaterAtWorldPos` wraps that method, returning waterY/depth *only where the client has actually constructed a visible RutFlow sheet*. On a dedicated server, `tryInitialize` sets `isClient=false` and skips its rendering model. Test with actual RutFlow source and `RF.isClient=false` confirmed **nil** for both world water queries.

It is therefore **unsuitable to supply Mud/RMS/MR physical wheel water state on the server**. A simplistic RC patch that calls RutFlow API to inform Mud would produce client-authoritative or missing values, not a canonical fluid model.

### RF/MUD-05 MEDIUM/HIGH — both can register SWS planes, different contact/collision semantics

RutFlow's client render graph registers up to 1500 visible near-level surfaces in `g_currentMission.shallowWaterSimulation`, with native foam/wave painting. Mud's client `LocalPuddleVisuals` also registers its puddle geometries in the same SWS service, while Mud creates **separate real ice colliders** near player/vehicles. There is no shared slot allocator, overlap-ownership token or camera-local renderer merge. Both may use rice-water material and mirror variants, so identical asset names are not proof they actually coalesce into one rendered water body. Avoid declaring them independently safe based on both supporting SWS.

### RF/MUD-06 MEDIUM — real topology/rut scale complements but does not equal physical hydrology

Mud: grid up to 256×256, ~8m per cell on 2km map/~16m on 4km, min basin depression ~6cm, persistent volume/ice and server authoritative runoff/infiltration/evaporation; no RE native completed-rut geometry event, so a fresh 10cm rut narrower than grid is **not necessarily a new basin**. RutFlow: 6m coarse triangles with 0.5m tire-local subdivision, 25cm measured rut shoreline and 100m contour; can visually show 2.5cm+ ruts and recheck height changes but has no real fluid-volume conservation. Its water is an **aesthetic micro-rut surface**, not a complementary additional physical reservoir.

**Big insight:** *the visual value is real, physical water ownership is not shared.* A deliberately source-aware cosmetic overlay could eventually use canonical Mud local moisture and only overlay micro-ruts **where Mud has no surface water**, with explicit mask/skip and no duplicate native SWS shape. That is a prospective capability, not current RutFlow 1.2.5.2 behavior.

### RF/MUD-07 MEDIUM — no active RE/RC compatibility or license path to a quick patch

Nothing in RC's existing MRMud/MRMudDraft/MudRMS/MudSoil/MRTireWear bridges writes water rendering; they solve tire/soil/engine physical domains. There is no "enable RutFlow 1.2.5.2" version gate in RC. Rudimentary indirect hooks into RutFlow private tile or global moisture methods would be brittle (scope is on clients), fail owner recheck and contradict **author's explicit prohibition on modifying its mod** without permission. A clean-room **separate optional overlay** on canonical Mud water/rut read APIs might be possible after actual need proof and licensing decisions, but has no source-level safe drop-in contract today.

## 3. RE terrain and external water alternatives

| Concern | RE / Mud owner | RutFlow interaction |
| --- | --- | --- |
| Native terrain height and recovery | **RE TerrainWriter / SpatialHistory**; prior native callbacks & clipping under investigation | RutFlow reads terrain/ruts and remeasures near camera, never writes native heightmap. Can display RE-created micro-ruts if those ruts actually exist. |
| Mud local wheel sink / wetness / soil | **Mud + MR** via RC source-scoped bridges | RutFlow lacks Mud local wetness input; no direct grip/torque/drivetrain writer. |
| Persistent surface-water basin and ice | **Mud 1.4** | RutFlow's display fill and save per-tile visual state do not replace Mud volume/snowmelt/ice. |
| Native ShallowWaterSimulation and rice material | GIANTS / both mods as clients | Duplicate water plane registration possible, no universal shared overlap suppression. |
| MapFlood | Alternative water/flood owner (independent audit). RutFlow contains a specific `getFloodAt` mask and optional saturation read | Can hide RutFlow under some MapFlood scenarios, **not evidence of Mud coexistence**; Mud itself flags MapFlood. Do not activate three water owners. |
| HSS/RP/RMS/Reifen | Physical contact/strain/tyre source | RutFlow player gfx and SWS interaction vs Mud wheel physical puddle/ice. No new direct Reifen API conflict, but new physics and visual mismatches need stable single-water baseline. |

## 4. Decision matrix and minimal no-guess A/B

| Setup | Functional result | Recommendation |
| --- | --- | --- |
| **A: Mud 1.4 puddles ON, RutFlow OFF** | Canonical hydrology, infiltration/snowmelt/ice and wheel sink; coarse basins may not visually fill every narrow rut | **Preferred primary-stack candidate after Mud 1.4 source PR #52 and game validation.** |
| **B: Mud 1.4 puddles OFF, RutFlow ON** | Preserve Mud soil friction/wetness plus RutFlow narrow-rut **visual water**. Not physically governed by Mud basins; independent fill from other providers/weather. Mud warns about RutFlow *presence* even when puddles disabled. | **Secondary experimental visual alternative** on cloned save, especially if RutFlow aesthetics matter most. Do not claim natural verified coexistence. |
| **C: Mud 1.4 puddles ON, RutFlow ON** | Two independently managed surfaces, moisture levels, SWS geometry and explicit Mud incompatibility alert | **Avoid in primary save.** Only disposable A/B to document overlap and prove/upstream a narrow specific contract need. |
| **D: Mud 1.3.9 (without puddle hydrology), RutFlow 1.2.5.2 ON** | Previous provisional WIT-style experiment, with better contour water and old Mud wetness mismatch | A valid **temporary old-version visual experiment** while not upgrading Mud to 1.4; still source-only, not retrospectively "VERIFIED". |

**Short game acceptance:**
1. Clone save with a representative **true 5–12 cm RE rut**, take before/after images and log; confirm rut is native geometry and do not modify terrain and water providers simultaneously in the same run.
2. **A** Mud 1.4 puddles ON, RutFlow OFF: one rain cycle, known existing ground depression, wheel actual sink under water, save/reload; test dry/flat unaffected; note whether micro-rut has a puddle (likely not guaranteed).
3. **B** Mud 1.4 puddles OFF, RutFlow ON: run `rfDebug` for moisture source, `rfProbe` for measured rut, inspect individual water in rut, player camera/collider, native waves and frame timing. Warning may appear. Compare visual water despite different physical moisture; old ZIP must be absent for new mod.
4. **C optional only if genuinely needed**: turn both ON in *disposable* session, compare Mud `LocalPuddleSystem:getDepthAt` vs RutFlow `getWaterAtWorldPos` at the **same sample points**, look for duplicate surfaces and repeated notices; capture result. Avoid console commands that overwrite production save water state until backup made.
5. Multiplayer/save: RutFlow only simulates its water on clients; if multiplayer important verify dedicated save and late join without conflating visual consistency with server hydrology. Remove old mod only from mods folder; **preserve** legacy XML for RutFlow auto-import until migration checked.

**Decision on bridge:** No RC physical/simulation patch and no RE water renderer build from this source audit. If after A/B the user values both domains, first request an upstream RutFlow *optional Mud wetness provider + external-basin coverage mask + no-private-overlap mode* and a Mud stable read-only basin API. Consider a clean-room opt-in RE micro-rut overlay consuming RE **completed** terrain writes and Mud authoritative wetness/water (not a second server water state) if upstream cooperates poorly and copyright/scene cost permits. Any patch must have **single authority, no SWS double registration, client/server separation and save/MP semantics**.

**Repository discipline:** docs-only increment to prior WIT audit PR #66. Separate Mud 1.4 source/compat PR #52 and RE terrain hydrology PR #76 remain independent, not merged automatically. No copied upstream code/assets; no RC/RE runtime files, no build, no source allowlist, no merge.
