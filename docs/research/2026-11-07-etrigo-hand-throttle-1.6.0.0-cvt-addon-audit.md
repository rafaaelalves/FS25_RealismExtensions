## 1. What v1.6 actually adds, with implementation detail

**Exactly one active feature domain:** optional **CVT Addon** hand-throttle delegation. Manual gearbox % throttle, manual closed-loop RPM PI (`RPM_KP=1.5` and `RPM_KI=0.8`), CVT speed target, shared RPM limit, cruise-control exclusion/input actions, local settings, serialization and Etrigo event networking **retain their v1.5 implementation**. There are no new PTO shaft, power consumer, traction, torque, wear, temperature, hydraulic wear, terrain or physics equations.

- New `CVT_ADDON_CYCLE = {PERCENT, SPEED, RPM_LIMIT}` for nonmanual vehicles with a recognized actual CVT Addon specification. Otherwise the old automatic cycle `SPEED→RPM_LIMIT` and manual `PERCENT→RPM→RPM_LIMIT` remain.
- `getCvtAddon(vehicle)` explicitly checks `vehicle.spec_CVTaddon.isVarioTM == true` and global `FS25_CVT_Addon.CVTaddon.VarioRpmAxis`. Absent addon, mismatching hardware or API => no active CVT % mode; no hard dependency, nil-safe.
- `getModeFitsGearbox` admits `PERCENT` on a nonmanual vehicle **only** if that CVT Addon integration is available. **Important:** other "CVT-like" transmissions from MR/RMS alone do not acquire the mode. This is a source-scoped capability, not generalized industry CVT support.
- On the **client's current active vehicle**, `onUpdate` computes `(spec.percent+0.5)/100` when system mode=PERCENT, nonmanual gearbox, motor on, cruise off. The +0.5 works around downstream percent truncation; 100% sends 1.005, which upstream `math.floor(value*100)/100` maps to 1.00. The source only invokes CVT Addon's **own** `VarioRpmAxis(vehicle,"SETVARIORPM_AXIS",value)` and stores last locally issued value in `spec.cvtAddonValue` to avoid repeated sends. It does **not** set motor torque or an external motor RPM floor itself.
- Server `Drivable.updateVehiclePhysics` override treats CVT-addon PERCENT specially: sets `spec.pedal=0` and does not force `axisForward`. The physical CVT addon remains the engine/hydraulic RPM input owner through its canonical setter. No new second proportional PI controller on CVT.
- On OFF/PAUSED/mode switch, `onUpdate` computes zero. `updateCvtAddon(0)` **does nothing if Etrigo's `spec.cvtAddonValue` is nil**, preserving a separately controlled external analog lever when Etrigo never commanded a positive percent. Once Etrigo did command a positive value, it sends zero on release. `onLeaveVehicle(wasEntered=true)` additionally sends zero directly, because its client update loop will stop running after exit.
- `spec.cvtAddonValue` is **client-local runtime bookkeeping** and is not included in HandThrottle streaming or savegame XML. A hand-throttle state/percent remains event-synchronized as before. On reconnect/reload, actual CVT Addon state belongs to its own synchronization/saving.
- Uses the global CVT class's `:VarioRpmAxis` rather than copying its internal `spec.HandgasPercent` write; the checked current upstream [CVT Addon official source](https://github.com/SbSh-DNA-ModDing/FS25_CVT_Addon_Dev/blob/main/CVT_Addon.lua) defines the method (near line 1591), truncates 0..1 input to 2 decimal places, raises dirty flags and transmits `SyncClientServerEvent`. This is a **real narrow integration API**, a positive design precedent for RE adapters.
- On vehicles *without* CVT Addon, only the new nil-guard path is introduced; original controls and physics are structurally unchanged. User need not install CVT Addon to use the new Etrigo release.

## 2. Exact-source and isolated tests, facts vs hypotheses

**All source tests below are tiny Lua mocks; no actual FS25 session, dedicated MP, engine/hydraulic reaction, CVT vehicle or FPS was run.**

**ETH16-01 POSITIVE — hardware/API detection and no duplicate motor writing.** The uploaded `HandThrottle.lua` loads in `texlua` with a GIANTS-shaped test global. The same mocked automatic vehicle:
- `spec_CVTaddon.isVarioTM=true` + upstream-style method makes PERCENT available; absent CVT Addon global or `isVarioTM=false` makes it unavailable.
- `updateCvtAddon(0)` does **nothing** if no value was previously commanded. An analog CVT state 0.71 was preserved.
- Etrigo 35% converted to 0.355 → simulated CVT Addon function truncated it to **0.35**. Repeating 0.355 sent no second event/callback. Releasing once sent **0** and a repeated OFF sent nothing.
- No RPM PI or pedal force was involved in these direct CVT setter tests. Source also confirms the server physics override clears pedal in that mode.

**ETH16-02 MEDIUM — engine-stop cleanup is deferred and input-focus-dependent (reproduced source test).** The release notes say **stopping the motor sets CVT Addon hand throttle to 0**. However, `HandThrottle:onStopMotor` only invokes `pauseHandThrottle`. It does **not** call `HandThrottle.updateCvtAddon(self,0)`. That cleanup is deferred to `onUpdate`, whose early guard returns if `not self.isClient` or `not isActiveForInputIgnoreSelection`. Isolated Lua test: command CVT 45%, call `onStopMotor` ⇒ Etrigo mode pauses but **CVT VarioRpmAxis not called with zero**; then call `onUpdate(...,isActiveForInputIgnoreSelection=false)` ⇒ still no zero; a subsequent active-input `onUpdate` **does send zero**. This is a **source-proven timing/lifecycle gap**; not evidence of a real-world stuck idle throttle, which depends on GIANTS stop and CVT Addon's own motor-lifecycle resets. **Upstream suggestion:** explicitly release the Etrigo-owned CVT value in the client stop path (with correct authority scope), without clearing someone else's axis input if Etrigo never owned a positive value.

**ETH16-03 MEDIUM — not a true control-lease system when external analog input is also active.** The code records only the *last Etrigo-issued* percent. If Etrigo sets 35%, another analog input subsequently sets 70%, and Etrigo then turns off, its zero cleanup **will set the CVT axis to zero**, superseding the analog's more recent value. That matches the author's explicit "pause/off sends zero" intent but means the documented "last moved wins" is only true between actions, **not a cooperative ownership token**. For RE design, a shared engine control arbiter with command ownership or current-actual-value compare-and-release would be stronger than unconditional reset after prior self-ownership. A real analog input test is still needed.

**ETH16-04 HIGH FOR UNTRUSTED MP — extra reliance on two pre-existing permissive event handlers.** Etrigo's `HandThrottleEvent.lua` is byte-identical to v1.5 and lacks explicit requesting-controller/farm permission check; the upstream CVT Addon `events/SyncClientServerEvent.lua:run` similarly applies incoming **full CVT state including `HandgasPercent`** for any synchronized vehicle then broadcasts, without checking the requesting player's control/farm. Both are **source-level missing authorization**; this audit did not exploit a live server. Etrigo's API path uses the CVT Addon's existing network event, not a new third custom event. Any combination should remain **not approved for public/untrusted MP** until upstream server-side ownership and per-vehicle control checks are validated/hardened. This also argues against copying the event model into RE, where `PTOStateEvent` has stronger requester authorization.

**ETH16-05 MEDIUM — independent RPM governors and CVT physical authority remain.** Etrigo's existing global `VehicleMotor.getRequiredMotorRpmRange` limiter and CVT speed cap still share effective motor policy with RE PTO/RC MRPTO/MR. The new delegation avoids a second pedal accelerator writer **only for CVT Addon % mode**; it does **not** make all other Etrigo modes safe to run simultaneously with RE or establish MR/CVT Addon/RMS drivetrain authority. Etrigo still pauses on operator exit whereas RE deliberately preserves unattended stationary PTO hand RPM. Keep prior 1.4/1.5 warnings and test with a single engine owner.

**ETH16-06 LOW/MEDIUM — UI/input sharing previous issues unchanged.** New `ETHT_*` action names introduced in 1.5 are retained in 1.6; 1.5 users' bindings do not need to be renamed *again*. 1.5's existing cruise action handoff restores other mods' input actions to `true` without proving their prior active state, and can defer release on focus loss; the relevant code is unchanged in 1.6. No new release notes claim it was fixed. The new CVT setter partly benefits from event dedup, but action ownership remains a separate concern.

## 3. RC / RE / MR / RMS cross-stack decision

| Component | Correct source-level ownership and next action |
| --- | --- |
| **RE PTO operator hand throttle** | RE's native PTO already has an operator-requested engine **minimum RPM** and handback state, including unattended operation. Etrigo 1.6 does not modify shaft ratios or request semantics, so no RE PTO runtime changes or new PI owner warranted solely because of v1.6. |
| **RC MRPTO / MR** | Existing MR engine/gearbox/PTO workload and RPM policy remain. Etrigo CVT addon branch forwards a *different mod's own hand throttle*, not an MR-specific guaranteed hydraulic RPM request. No generic MR wrapper or new RC version gate justified. |
| **CVT Addon (optional)** | New source-verified narrow delegated UI integration, but CVT Addon transmission physics and its large state-sync event have their own authority; MR/RMS drivetrain compatibility is **not verified** by this Etrigo source audit. Do not advise blindly installing CVT Addon just for Etrigo buttons. |
| **RMS 0.13.0.1** | Owns real wear/faults; engine, alternator, CVT slip/damage sensors may interact with **CVT Addon** physical transmission. Etrigo's new adapter doesn't implement wear. Review actual vehicle if separate CVT Addon trial is desired. |
| **Mud / Reifen / RE terrain V3** | New v1.6 branch reads no wheel traction/soil/terrain surface and writes no wheel radius, sinkage or height. No direct new physical collision. |
| **Player UI / Vehicle Inspector / MP** | Existing 1.5 input-ownership caveats remain, and CVT Addon adds second event-authority chain. No source-proven multiplayer safety. |

**Good pattern to learn for the RE:** _capability detection → delegate to external mechanical owner through a versioned API → only send on change → explicit pause/release policy → do not force pedal/duplicate drivetrain power._ That is exactly the direction for a future clean-room `OperatorEngineGovernor`, and potentially for HSS/RMS capability controls. **But** the CVT Addon setter is not a generic engine-hydraulic API; the RE should use native MR/GIANTS arbitration unless the user actually wants to add that particular mod, with permission/MP and ownership checks.

## 4. Minimal real test if CVT Addon is used (optional)

On a disposable save, with the **RE operator hand throttle disabled for the same vehicle** or otherwise physically isolated:
1. One true CVT machine that already has CVT Addon capability; system OFF: check analog addon lever remains untouched; cycle OFF→%→speed→RPM limit→OFF, keys increment correctly and mode percent does not impose extra wheel driving input.
2. Test engine on with hydraulics/loader movement; compare CVT Addon real engine RPM/actuator speed, motor load, fuel and any MR/PTO effects at 0/30/60% command. The source *forwards the value* but does not guarantee hydraulic speed reflects it on all machine models.
3. Set 35% with Etrigo, then analog 70%, pause/engine stop/exit. Capture actual CVT HandgasPercent and onUpdate focus; check whether zero is immediate, deferred or overwrites the analog input. Repeat with motor stop while switching vehicles.
4. Test CVT km/h mode OFF (speed cap restoration) and vanilla/Vehicle Inspector cruise ownership as carried over from 1.5. No untrusted dedicated multiplayer until authorization addressed.

If CVT Addon is *not* installed, no special test campaign: the new percent-CVT mode is unavailable, and the user's existing RE PTO remains primary.

## 5. Decision and repository discipline

**Verdict:** positive **external API integration design lesson**, **not** a reason to switch RE PTO governance or introduce CVT Addon into the normal stack. Source-and-isolated-mock acceptance for Etrigo 1.6 **as an optional mod**; deferred CVT clear-on-stop and inherited MP/action ownership issues deserve follow-up.
