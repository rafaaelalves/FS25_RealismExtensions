# Realistic 4x4 Traction System static findings

Baseline: exact shipped `1.6.0.0` ZIP SHA-256 `eff66ca5b261cfefc76c776dfd41ac225199d832f65b8d7e54146bac2f73c09c`.

Evidence labels:
- **CONFIRMED_STATIC**
- **STRONG_CANDIDATE**
- **DESIGN_RISK**
- **POSITIVE_PATTERN**
- **RUNTIME_PENDING**

## 4WD-01 Sensor -> model -> actuator separation
**POSITIVE_PATTERN**

The mod isolates much of its reasoning in `FourWDTractionModel`.

This is substantially easier to test and improve than embedding all policy into the physical differential writer.

## 4WD-02 Reason-coded automation
**POSITIVE_PATTERN**

Decision state carries reasons such as slip, prediction, brake, implement, low-speed, hold, road, steer and descent.

Explainability is valuable for:
- HUD;
- logs;
- tuning;
- runtime validation.

A future advisor should preserve reason codes/masks.

## 4WD-03 Hysteresis and minimum engagement hold
**POSITIVE_PATTERN**

Separate slip engage/disengage thresholds plus `engagedUntil` prevent rapid chatter.

This is a good general automatic-drivetrain pattern.

## 4WD-04 Launch grace and brake-slip rejection
**POSITIVE_PATTERN**

The source explicitly suppresses unreliable launch/near-zero slip and ignores wheel-slip generated by braking for a period.

This is a practical improvement over naive "slip > threshold" AUTO logic.

## 4WD-05 Slip filters are update-rate dependent
**CONFIRMED_STATIC numerical design limitation**

`smoothedSlip` uses fixed per-update weights:
- different rise/fall weights;
- fixed lock smoothing.

No `dt` normalization is applied.

Effective filter response changes with FPS/update rate.

Clean redesign:
- preserve asymmetric rise/fall behavior;
- express it as time constants;
- compute alpha from elapsed time.

## 4WD-06 Smart mode ignores brakeEngage=false
**CONFIRMED_STATIC defect**

Binary braking reason respects:
`cfg.brakeEngage == true`.

The Smart continuous target independently takes the max with:
- brake > 0.3;
- speed > 3;
- target 1.

It does not check `cfg.brakeEngage`.

The shipped readme/config says braking is disabled by default, yet Smart can still request full 4WD on brake.

## 4WD-07 Global weather wetness is used as traction state
**DESIGN_RISK**

Fallback demand computes field/road traction coefficient from global `weather:getGroundWetness()`.

Target stack already has richer local physical state.

A drivetrain advisor should never downgrade to global wetness when RC/Mud can provide local wheel/ground state.

## 4WD-08 Direct private Soil Draft / MR reads
**DESIGN_RISK / integration coupling**

The mod gains better demand inputs from:
- Soil Draft Physics globals;
- direct MR child `mrLastForce`.

The concept is good; the coupling is not.

Target implementation should consume normalized providers.

## 4WD-09 Lowered implement is itself an engagement reason
**DESIGN_RISK**

AUTO can engage because:
- implement is lowered;
- on field;
- steering is below threshold.

The source can separately compute real draft, yet lowered state remains a direct reason/keep condition.

This can over-engage with low/no draft.

Use actual tractive demand as primary signal; lowered state should be context at most.

## 4WD-10 Low-speed field arming is coarse
**DESIGN_RISK**

After a delay, low speed + lowered implement + field can request full assistance.

This may help gameplay but conflates:
- intentional slow precision work;
- high drawbar demand;
- traction shortage.

A better model uses actual traction reserve/motor load/draft.

## 4WD-11 Terrain anticipation uses only two forward height samples
**DESIGN_RISK / prototype-quality**

The lookahead is speed-scaled and samples half/full distance.

That is cheap and useful, but:
- abrupt terrain noise can dominate;
- it does not follow a planned AI/path curve;
- it predicts grade, not traction state.

A better advisor can low-pass several path-aligned samples and combine them with actual demand.

## 4WD-12 Descent model is heuristic
**DESIGN_RISK**

Descent demand appears when:
- downhill grade crosses a fixed threshold;
- child mass is sufficiently large relative to tractor.

This approximates the value of four-wheel braking.

A more physical model compares required braking/retarding force against the available primary-axle braking/traction capacity.

## 4WD-13 Center differential identification is structurally ambiguous
**CONFIRMED_STATIC architecture risk**

The scan treats every differential with two differential children as a center candidate and overwrites `centerDiffPosition` as it iterates.

The last matching differential wins.

It then labels child 1 front and child 2 rear without geometric/steerability verification.

This is inferior to the audited RMS topology inference and is unsafe to absorb.

## 4WD-14 2WD retains the full graph
**CONFIRMED_STATIC ownership/model difference**

When disengaged the source applies approximately:
- center torque ratio `-0.00001`;
- very high allowed speed ratio.

It does not install a primary-only graph.

RMS already implements a stronger semantic 2WD plan by changing effective topology.

## 4WD-15 Differential graph can be rebuilt repeatedly during ramps
**CONFIRMED_STATIC performance/ownership surface**

Physical overrides mark the graph dirty.

The source can rebuild all differentials using:
- `removeAllDifferentials`;
- `addDifferential`;
- `updateMotorProperties`.

A 120 ms minimum interval throttles rebuilds, but engagement/lock ramps can still cause repeated graph reconstruction.

This is both an overhead and cross-mod ownership surface.

Do not reproduce it beside RMS.

## 4WD-16 Center lead ratio uses radiusOriginal preferentially
**CONFIRMED_STATIC state inconsistency**

Center ratio computation takes:
`radiusOriginal or radius`.

The later CTIS scan explicitly takes:
`radius or radiusOriginal`
because `radiusOriginal` may be the unadjusted XML/source value.

Thus center lead computation and pressure subsystem do not use the same effective-radius semantics.

In a stack with dynamic structural/effective radius, this can make lock lead stale/inconsistent.

## 4WD-17 CTIS writes wheel physics radius
**CONFIRMED_STATIC ownership conflict**

Pressure simulation changes physical wheel radius and marks wheel position dirty.

Mud already owns target-stack pressure/CTIS.

This subsystem is rejected for RE.

## 4WD-18 Global WheelVisualPartTire overwrite
**DESIGN_RISK**

The mod globally wraps `WheelVisualPartTire.update` for its tire flattening.

There is an install guard but no teardown/identity restoration contract.

Even if composable through `Utils.overwrittenFunction`, it expands the global hook surface for a capability the target stack does not want this mod to own.

## 4WD-19 Toggle event authorizes farm, not vehicle controller
**CONFIRMED_STATIC authority weakness**

Client-originated 4WD/lock request checks that sender belongs to the owner farm.

It does not require the sender to control the target vehicle.

Same-farm remote mutation may therefore be possible.

Future server API should validate current controller/authorized interaction.

## 4WD-20 Tire-pressure event has no sender authorization
**CONFIRMED_STATIC**

Client-originated pressure target is directly applied then rebroadcast.

No ownership/controller/farm check is present.

## 4WD-21 CTIS preset event has no sender authorization
**CONFIRMED_STATIC**

Same issue as pressure target.

## 4WD-22 Broad vehicle-category filtering precedes topology proof
**DESIGN_RISK**

The specialization is injected widely, then store category substrings and filename exclusions narrow applicability.

The mod eventually requires a center differential, which prevents some false positives.

Still, capability/topology classification should be primary; store-category names should not determine drivetrain semantics.

## 4WD-23 Crawler handling is partly model-list driven
**DESIGN_RISK / intentional compromise**

Two-track machines are explicitly excluded by filename patterns while some four-track configurations remain eligible.

This reflects real topology differences, but the classifier is a vehicle-name database rather than deriving the mobility topology.

RMS/provider state is a better source.

## 4WD-24 Server owns automatic decisions and differential physics
**POSITIVE_PATTERN**

Clients receive state; the server runs the automatic decision and physical writer.

This is the right multiplayer authority direction despite manual event authorization gaps.

## 4WD-25 Requested level is separated from actuator ramp
**POSITIVE_PATTERN**

Smart mode can output a continuous target level while the physical layer moves toward it over configured time.

This separation is worth preserving in any richer RMS AUTO controller.

## 4WD-26 Load/draft-aware traction reserve concept
**POSITIVE_PATTERN**

When available, the model can use actual draft, actual axle load and effective traction coefficient instead of only static mass.

This is one of the strongest ideas in the package.

## 4WD-27 Pressure capability is incorrectly bundled with drivetrain capability
**DESIGN_RISK / rejected ownership**

The mod's modern scope includes universal/manual tire pressure and onboard CTIS behavior.

These are distinct hardware/state domains.

A clean architecture does not make "4WD system" owner of tire pressure.

## 4WD-28 Internal version comments diverge from published package version
**CONFIRMED_STATIC documentation issue**

Several files/readme sections retain internal `2.x` development history while shipped modDesc/readme package version is `1.6.0.0`.

The package explains some of this intentionally, so it is not a runtime defect, but version-gated compatibility must use the modDesc/exact hash rather than source-comment version text.
